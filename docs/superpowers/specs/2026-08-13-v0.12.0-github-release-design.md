# v0.12.0 GitHub Release Design

## Objective

Publish GitHub Release `v0.12.0` from the exact reviewed `main` state while
keeping `CHANGELOG.md`, package metadata, the Git tag, and the generated GitHub
Release truthful and mutually consistent.

## Current state

`nori.json`, `.nori-version`, `README.md`, and `docs.md` already declare
`0.12.0`. `CHANGELOG.md` records that version as an unpublished package state,
and GitHub has neither tag nor release `v0.12.0`. The most recent published
release is `v0.10.0`. Versions `0.11.0` and `0.11.1` are intermediate package
states that were never tagged or published.

## Release preparation

A dedicated pull request changes only the release ledger and its executable
contracts. It moves the complete `0.12.0` section from `Unreleased package
states` to `Tagged release history`, uses the effective publication date
`2026-08-13`, and preserves every existing release bullet. The unpublished
`0.11.1`, `0.11.0`, `0.9.1`, `0.9.0`, and `0.8.0` entries remain unpublished
and in semantic-version order.

Tests must reject any state where `0.12.0` remains unpublished, appears in both
taxonomies, has an incorrect date or heading, loses a bullet, or diverges from
the package metadata. No package version is bumped because `0.12.0` is already
the approved release version.

## Tag and automated release

After the preparation pull request passes local validation, independent review,
CI, and Security, merge it into `main`. Create one annotated tag `v0.12.0` on
that exact merge commit and push only that tag. The existing `Release` workflow
then runs the complete package gate, verifies that the tag version equals
`nori.json`, and creates the GitHub Release with generated notes.

Do not create a manual release with `gh release create`, force or replace a tag,
or publish a release from an unmerged branch. If the tag workflow fails, retain
the tag and diagnose the workflow; do not manufacture a release that bypasses
the failed gate.

## Acceptance

- The preparation PR is merged and `main` is clean and synchronized.
- `CHANGELOG.md` lists `0.12.0` exactly once under tagged history with date
  `2026-08-13`; every prior bullet remains present.
- All package metadata remains at `0.12.0` and all release-history tests pass.
- The annotated tag `v0.12.0` points to the exact preparation merge commit.
- The tag-triggered `Release` workflow succeeds without manual bypass.
- GitHub exposes a non-draft, non-prerelease `v0.12.0` release whose tag and
  target commit match the validated state.

Publishing this GitHub Release does not upload the package or its components to
the Nori registry. Registry publication remains a separate operator-authorized
operation.
